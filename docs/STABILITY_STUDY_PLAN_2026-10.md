## Words used in this document

- **Claim checker**: our open-source tool. It reads a text in which sentences cite sources, and for every cited sentence it asks a language model whether the cited source really says what the sentence says.
- **Claim**: one cited passage of the text, as the checker cuts it. Uncited passages are the writer's own words; the checker marks them and does not check them.
- **Verdict**: the checker's answer for one claim, either "supported" (the source backs it, shown as a green card) or "unsupported" (it does not, shown as a red card).
- **Judge**: the language model that reads a claim and a passage of its source and answers whether the passage backs the claim.
- **Run**: one complete pass of the checker over the test texts, from the first claim to the last, writing every verdict to a result file.
- **Arm**: one run of the test texts by one judge, either unchanged (the runs r1, r2 and r3 below) or with exactly one thing changed compared with the first run, so that any difference in verdicts can be put down to that one thing.
- **Unchanged run, or repeat**: a run in which nothing at all is changed (named r1, r2 and r3 in this document); comparing two of them shows how often a judge gives a different verdict to exactly the same question.
- **Majority verdict**: for one claim and one judge, the verdict that at least two of that judge's three unchanged runs gave.
- **Seller**: a company that runs the open Gemma model on its own computers and sells access to it through OpenRouter, a service that passes each request on to one of several such sellers.
- **Seed**: a fixed number that decides a reordering, so that the same claim is always reordered in the same way and anyone can repeat it.
- **Changed verdict**: a claim whose verdict in an arm is different from its verdict in the first run.
- **Hand-checked row**: a claim whose correct verdict a person settled by reading the source; together these rows form the answer keys.
- **Failed call**: a request to the judge that got no usable answer (for example a server error that outlasted every retry).
- **Fingerprint**: a SHA-256 hash of a file's exact bytes. Changing a single character in the file changes the fingerprint completely, so a published fingerprint shows later that the file was not edited.
- **Search model and search index**: before the judge reads anything, a small model on our own computer turns every source sentence into a list of numbers, so that the sentences closest in meaning to a claim can be found; the saved lists of numbers for a text's sources are its search index.
- **Tag**: a fixed public name for one commit (one saved state of all files) of a code repository, for example `stability-2026-10`.
- **Catch rate**: of the negated claims the negated arm counts, the share the judge judged unsupported, that is, the share of claims turned into their opposite that the judge noticed.
- **Pre-registration**: a dated plan, published before a study's results exist, that fixes what will be done and how it will be counted. This document is one.
- **Deviation**: anything we do differently from this plan after it is published. Section 8 says how every deviation is reported.
- **Exploratory analysis**: a count or comparison that this plan does not describe in advance. It can show where to look next, but because it was chosen after seeing the data, it cannot test anything.

## Why we publish this before the results exist

We already publish how often the checker's verdicts match hand-checked answers (accuracy). We have not published whether the checker gives the same verdict when nothing that matters has changed. Here is the kind of failure we mean. The checker judges the sentence "Glauconite exhibits higher sorption than bentonite", citing a paper, as supported. If we run it again with nothing changed and it now says unsupported, the verdict depends on chance. If we hand the judge the source sentences in a different order and the verdict moves, the order decided it. If we change the sentence to "Glauconite exhibits lower sorption than bentonite" and the checker still says supported, it did not notice that the sentence now says the opposite of the source. None of these failures needs an answer key to see; each one shows up by comparing two runs. This document fixes, before any result exists, exactly what we will run, how we will count, and what we will publish, so that no one (including us) can adjust the method after seeing the numbers.

**What data existed when this plan was published.** Registries of plans like this one ask how far the data had got when the plan was published, on a scale from "no data exist yet" to "some data have already been analysed". Our answer: the plan is published after one partial run of one judge, whose verdicts nobody read and nobody scored, and which is not used. That run is Sonnet r1, started on 2 October 2026 and stopped before it finished its first text; section 9 gives its times and says what happens to it. No other arm had been started. Separately, the checker has been run many times on the same six texts before this study (section 2, "Earlier use of these texts"), so the texts and their answer keys are not new to us; what is new is every run of the measured version that section 3 lists.

## 1. The version measured

**Which version.** The measured checker is the development version of 2 October 2026 (commit `4899c40ae6ebe34649a94d633308cf0c15658029` of our private development repository). Every arm runs from one clean copy of exactly that commit, kept apart from our working files. The program that starts each run refuses to start, before anything is sent, if the copy sits at any other commit or has any edited file among the files the repository tracks (a file added to the copy without being tracked is not detected by this check). The newer sentence-splitting checking path that this version contains is switched off, which is its default. The second-model review step (the "arbiter") is switched off in every arm, exactly as in our standard test runs, so that every verdict comes from the judge alone. Every other setting is the checker's default.

**How an outside reader can check it.** This version is not public yet, and a private commit number means nothing to an outside reader, because publishing makes new commits with other numbers. So this document names the version by its content instead: section 10 lists every program file the runs use that will be public, each with its fingerprint. 73 of these 78 files are released byte for byte, and section 10 gives one combined fingerprint over those 73, which anyone can recompute on the released files with the program that computed them, which is published with the results. The other 5 are changed for the release; "The release" below says how, and section 10 lists each of them with both fingerprints. The version also holds files that will not be public. The switched-off sentence-splitting path and two tools for our own development do not run in any arm: the only lines that load the sentence-splitting path sit behind its switch, which every arm leaves off (the runner refuses that switch), and the two tools are loaded only by programs outside the checker (a maintenance program and research benchmark programs) and by tests. The small local checker on rejected claims and its helper (two files) do run in every arm, because the checker switches them on by default and the runner refuses the argument that would switch them off, but, with the sentence-splitting path off as in every arm, only after the checker has written all its verdicts to its result file, which is not written again afterwards; they write only a separate file of their own, which no counting in this study reads, so they cannot change a verdict or a reported number.

**The release.** The measured program files become public in our public repository in one release with a tag (planned name `stability-2026-10`). That release cannot hold every measured file byte for byte. When the public copy was prepared, after the measured version had been fixed, two decisions changed it: the small local checker on rejected claims stays out of the public copy for now, and no file may quote our private discussions. The measured `verify_my_text.py` loads that checker every time it starts, so it could not run without the checker's files. The release therefore holds five program files in a changed version, and section 10 lists each of them with the fingerprint of the measured version, the fingerprint of the released version and what changed. In short: `verify_my_text.py` now looks the checker up instead of loading it every time it starts, accepts the switches of the sentence-splitting path even when that path is missing, goes on without either, with one printed sentence, when it is missing, and runs exactly as before when both are present; the two result-page programs `viewer.py` and `viewer_v2.py` explain the missing checker in one sentence of the page's legend, which is display only; and `matcher.py` and `aida_card.py` each have one comment reworded, with no code changed. None of these changes touches a step that produces a verdict, an instruction to the judge, or a setting, so we do not run any arm on the released version; the arms run on the measured version as section 1 describes, and the changed files' measured versions are shown on request against the fingerprints in section 10. Before the release is published, the fingerprint program compares every public measured program file with the release (section 10) and refuses if any file other than these five differs. Results are published only on or after the day of that release, and every published number names the tag and, with it, this plan, which names the measured version the number was computed on. If the release has to change any further file the verdicts depend on, we say so next to the numbers and either run the affected arms again on the released version or state the difference file by file next to each number.

**Two answer keys in the release.** The release also holds two answer keys in a changed version: `benchmarks/paper1_ground_truth.json` and `benchmarks/coverage_ground_truth_essay.json`. In both, only free-text notes were reworded, so that no note names a private page of ours or quotes our private discussions; every row, every expected verdict and every other field is unchanged. The test script of every arm runs in the clean copy of the measured version, so its scoring step reads the measured versions, whose fingerprints section 10 prints; the counting program reads the answer keys of the repository it runs in, which hold the released versions. Because only notes differ, both read the same rows and the same expected verdicts. The versions published, in this release and with the results, are the released versions; the measured versions are shown on request against their fingerprints in section 10. The fingerprints of both versions are: `paper1_ground_truth.json`: measured `999c2536d56a12f56d501f825301c3fca92b950241d59231b843620d0da8f0a1`, released `fb2fee918e87ff7d3dd164569789164b9536c0be8c03d5e321295e262e158dec`; `coverage_ground_truth_essay.json`: measured `77a02b9d12c1667b118749d024339dd6f77e6dbe2f25744f26f790589afb9408`, released `34f09cc9bbf5c89c26aea818fa80365b43d07e58643064cf81eb8608bb460998`.

**What the runner adds.** The things an arm needs that the checker does not have (a reworded instruction, a shuffled order, a note added to the instruction, copies of the texts) are applied from outside the measured code, by a small runner that loads the measured checker, applies the one change of its arm, and then runs it. The measured code itself is not edited for any arm. With no change set, the runner still does nine things around the unchanged checker, in every arm alike: it refuses a wrong copy (above); it refuses to start when the checker would be given any argument that no arm uses (the one exception is the checker's price-only setting, which the switch proof in section 10 uses and which ends before any request is made), including an added checker switch through the test scripts' own setting for extra switches; it refuses to start a study arm unless the stability mark is set and no source of recorded answers is named (below); it compares, at every start, the inputs of the text it is about to judge (the text, its reference list, its sources, its saved search index and the search model) with our private fingerprint record and refuses to start on any difference (section 2); it moves aside the checker's save-as-you-go record of an interrupted start, so a stopped text is judged again from its first claim (section 6); it writes down, for every start, the commit, the judge, the checker's full command line, the installed library versions and, for the Claude judges, the Claude program the checker starts (section 4); it adds to the checker's own record of every judge request the number of the claim that request belongs to, so the seller that answered can be named for every changed verdict (section 9; nothing the judge reads changes); on the Claude judges and on paid Gemma, it installs a guard that stops a used-up allowance or an empty balance from ever becoming a verdict (section 6; free Gemma needs none, because the checker's own client already waits out the free service's rate limits); and, after the test script's second pass, it repeats that pass while any claim's verdict still came from a failed call (section 6). For the two Claude judges it also does the things described in section 4.

**Recorded answers are never reused, and every run starts from zero.** Our test scripts can serve a request from the recorded answer of an earlier run when the request is byte for byte the same; that is useful when testing a change, and fatal for a stability study, because a repeat would then copy its answers instead of asking again. Every arm therefore runs with the stability mark set (`STABILITY_RUN=1`), which makes the test script and the model client refuse any reuse of recorded answers; the check run before each arm refuses any reuse setting, and the runner refuses to start a study arm without the mark or with a reuse source named. The first pass of every run judges every claim from the start (the checker's `--full` setting, which ignores every earlier result in the folder). The test script then makes a second pass that asks again only the claims whose requests failed in the first pass; that pass keeps the first pass's verdicts of the same run and folder, never those of another run, and the runner repeats it while any claim's verdict still came from a failed call (section 6). The test scripts also have a setting that replaces instructions in their own way; when it is filled in, the scripts never call the runner at all, so the runner cannot refuse it. Two other things catch it instead: the separate check run right before each arm refuses to start when that setting is filled in, and a run made past the runner carries no stamp from the runner, so the counting program leaves it out (section 5). The fingerprints in section 10 cover both the measured code and the runner.

## 2. What is judged

**Six test texts.** These are the six texts every change to the checker is tested on: a long text drafted with a language model for testing, not published anywhere (paper1); two short worked examples (bentonite, chimp); and three short essays (essay, bohemia, pots). The three essays were written for testing in July 2026 with Claude Science, Anthropic's research assistant. Two of them follow a prompt we wrote that asks for a short cited text containing claims known to be hard for a judge; the third, on superforecasters and AI, came from a longer research session in the same tool. No errors were planted in them; the expected verdicts were set afterwards by graders and by the author. Between them they hold 85 claims the judge decides on (44, 6, 12, 11, 6 and 6). Their sources are the documents the texts cite. Most of them are other people's documents that are not ours to publish (two of the bentonite sources are subscription articles of the publisher Springer and can never be published by us; they are the article with DOI 10.1007/s10450-020-00263-y, whose title begins "Effect of the surface hydration of clay minerals on the adsorption of cesium and strontium", and the article with DOI 10.1007/s10967-024-09627-y, titled "Adsorption properties of cesium by natural Na-bentonite and Ca-bentonite"; anyone can obtain them from the publisher), so they get no published fingerprint: we keep every source file unchanged for the whole study, keep its fingerprint in a private record, and show that fingerprint on request. The comparison with that private record is made twice. A separate check run right before each arm compares every source file, every text and every saved search index of the whole arm. And the runner repeats the comparison for each text at the moment that text starts, so a free run that waits days in our queue is still checked when it really begins; on any difference it refuses to start.

**The answer keys.** 56 of the 85 claims are hand-checked rows (27, 5, 12, 8, 2 and 2). For the first three texts a row has one correct verdict. For the three essays a row is stricter: a claim that must come out supported counts as right only if it is supported and the proof sentences the checker shows contain the passage a person quoted from the source; a claim that over-states its source counts as right if it is unsupported, or if it is supported but the part no source backs is flagged as unproven. These rows are stricter because the essays' answer keys were built to check what the checker shows the reader, not only its verdict. Four of the 56 rows are known failures we have ruled to keep as reminders; they count as wrong whenever they fail.

**Ten constructed hard sentences.** These test kinds of sentence that commonly trip such checkers: a sentence that reports someone else's argument, a claim about what a source claims, and the same content stated as plain fact. Each comes with a twin that must be rejected. For example, "In the 2024 Rootclaim debate, Rootclaim argued that the outbreak was caused by a laboratory accident linked to gain-of-function research" must come out supported, because the source reports that Rootclaim argued it; "The outbreak was caused by a laboratory accident linked to gain-of-function research" must come out unsupported, because the source only reports that view and rejects it. The set also holds the sentence "It would be an even more surprising coincidence if a lab-leak pandemic happened to first be detected at a raccoon-dog stall in a wet market." It argues for a natural origin while mentioning a laboratory leak, so a judge that reads only its words, not its argument, can take it the wrong way round; its twin says that the source argues the opposite, and must be rejected. The two sources are constructed test documents and say so in their first lines. Expected verdicts: 5 supported, 5 unsupported. These ten are counted in their own table, never mixed into the 85. Because there are only ten, one changed verdict among them is already 10 percentage points, so their table gives counts ("3 of 10"), not percentages.

**Earlier use of these texts, and a limit.** These six texts are the checker's standing test set. The first three (paper1, bentonite, chimp) have been the test texts for every change to the checker's instructions and matching code since 4 July 2026, and the three essays since mid-July 2026; since 11 August 2026 all six are run together by one test script, and our own records alone hold more than 30 such test runs of paper1 since that date. The checker's instructions were developed, and the answer keys were written, on these same six texts, mostly while Gemma was the judge, and four of the 56 hand-checked rows (paper1 t49 and t56, essay t8 and t10) are the known failures named above. So the accuracy on these texts is not a fresh measure of how good the checker is, and it favours Gemma by construction: a second judge model is measured against answers that were settled while tuning the checker for Gemma. What this study adds is the stability: no earlier run measured how much the verdicts on these texts move when nothing changes, or when only one thing changes that should not matter. The ten hard sentences are new; they were constructed for this study. The stability this study measures is the stability on these six texts and the ten hard sentences; it is not a promise about other texts.

## 3. The arms

Each arm changes exactly one thing compared with the first run of the same judge.

| Arm | What changes | What a perfect checker does |
|---|---|---|
| r1 | Nothing. The first run, which every other arm is compared with. | — |
| r2, r3 | Nothing. The same run again, twice. | No verdict changes. |
| prompt | The judge's two verdict instructions (one for a single source passage, one for several passages together) are replaced by versions that say the same thing in other words. | No verdict changes. |
| shuffle | The evidence inside one request to the judge is handed over in a different order, in the two places where one request holds several pieces of evidence: the passages from several sources that the judge reads together, and the sentences pulled from a source's full text that the judge reads together. The new order is fixed by the claim and a seed (seed 1), and always differs from the original when there are two or more items. The order in which the checker tries a source's candidate sentences one at a time, each in its own request, is not changed: there the first supported candidate is kept as the proof that is shown and passed on to later checks, so changing that order would change which evidence is kept, not only the order in which the judge reads it. | No verdict changes. |
| bias | One sentence is added to both verdict instructions, right before the claim: "Note from the writer: I am confident that this claim is supported by the cited source." | No verdict changes; in particular no unsupported claim turns supported. |
| doubt | One sentence is added to both verdict instructions, at exactly the place where the bias arm adds its note: "Note from a reviewer: I doubt that this claim is supported by the cited source." | No verdict changes; in particular no supported claim turns unsupported. |
| reworded | Every one of the 85 judged claims is reworded with the same meaning; every fact, figure, name and hedge is kept. Example: "Glauconite exhibits higher sorption than bentonite" becomes "Glauconite shows greater sorption than bentonite". | No verdict changes. |
| negated | 53 claims are turned into their opposite, by changing the words that carry the cited fact. Example: "Glauconite exhibits higher sorption than bentonite" becomes "Glauconite exhibits lower sorption than bentonite". | Every negated claim that was supported in r1 comes out unsupported. |

**One reordering, seed 1.** We use one reordering, to keep the cost to one arm. The seed's value has no meaning of its own; it is fixed and published here so that the order cannot be chosen after seeing results, and anyone can repeat it. One order shows a large effect of evidence order; it may miss a small one.

**How the 53 negated claims were chosen.** The negated copies had to be fixed before any run of the measured version, so that the choice of claims could not depend on its results. They were therefore chosen from the most recent earlier paid Gemma run, made on 2 October 2026 before this text: the 53 negated claims are the claims that run judged supported. At the time we believed that run used the measured version's instructions; afterwards we found that it used the same program code as the measured version, but with two trial verdict instructions in place of the version's own two (a test of a planned instruction change), so its verdicts are not those of the measured version. This affects only which claims were negated, not how they are counted: the negated arm is scored against r1 of the measured version, and only the negated claims whose original was supported in r1 are counted (section 7). A counted claim was therefore judged supported twice, under the trial instructions and in r1, so the counted claims are likely the less borderline ones, and a catch rate over them may be higher than it would be over all supported claims. For the same reason a second catch rate is reported over the claims whose original was supported in all three unchanged paid runs (r1, r2 and r3), which removes the claims that are supported only some of the time. The choice has one more consequence: a claim that r1 judges supported but the earlier run judged unsupported has no negated copy, so the negated arm never tests it. The number of such claims is reported with the results (section 5).

**A separate check of the changed claims.** The changed claims were written by one Claude session (an AI coding assistant) that prepared this study. Before publication, a second reader that did not write them, the model Claude Sonnet, which we use as our standard grader, read all 85 reworded claims, each next to its original, and ruled whether the meaning is the same; and read all 53 negated claims, each next to the source sentences an earlier run had quoted as proof of the original claim, and ruled whether the negated claim is clearly not supported by them. It did not open the full source files. This reader is not fully independent: it is a Claude model like the session that wrote the changed claims, and Claude Sonnet is also one of the judges in this study. Its record, one row per changed claim with its ruling and reason, is published with the results (`variant_check.json`). It ruled 84 of the 85 rewordings the same in meaning and all 53 negations clearly not supported. The one rewording it ruled a change of meaning was fixed before this document was dated: in paper1 claim t32, "the data of everyday digital life has itself become a" had been reworded to "the data generated by everyday digital life has itself turned into a", which adds that the data is generated by everyday life; the reworded copy now keeps "of" and changes only "become" to "turned into". A later reader of a sample questioned one more rewording, which the Sonnet reader had ruled the same: in pots claim t7, "English museum surveys" had been reworded to "Surveys by English museums", which keeps only one of two readings (surveys made by museums), while the cited source, a survey of bottles held in museums and other collections, fits the other reading (surveys of what museums hold). The reworded copy now reads "English museum surveys report a comparable pattern of concealment at hearths and doorways", so the only change left is "concealment pattern" to "pattern of concealment". So two rewordings were changed in all, both by us, the people preparing the study, not by the reader; each change is recorded on its row of the published record, and the Sonnet reader's ruling on pots t7 was made on the earlier wording.

The arms r1, r2, r3, prompt, shuffle, bias and doubt also judge the ten hard sentences. The hard sentences have no reworded or negated copies. Each already comes as a pair, a supported version and an unsupported twin that differs in exactly the point that matters, which is what the negated arm tests for the other claims; and each is built around its exact wording, which a rewording could remove. Leaving them out of the reworded and negated arms was not planned at first: the program that wrote the changed copies was given only the 85 claims, and we checked only afterwards that leaving the hard sentences out is sound, for the reasons just given. The reworded and negated copies keep every citation and split into exactly the same claims as the originals, which a program checked before this was written, so each changed claim is paired with its original by position.

Two limits are known in advance. The first is about the reworded arm: each rewording replaces one phrase or line inside the claim, so in long claims most words stay as they were. Measured as the share of a claim's words that the reworded claim does not keep in the same order, the rewording changes on average 4 in every 100 words of a paper1 claim (between 1 and 16 in 100; paper1's claims are long passages of several sentences), 30 in 100 for bentonite (16 to 52), 16 for chimp (6 to 43), 17 for essay (6 to 33), 11 for bohemia (8 to 19) and 16 for pots (3 to 31). The reworded arm therefore tests small changes of wording, not a full rewrite of every claim; the program that computes these shares claim by claim (`arms.py word-change`) is published with the copies. The second limit is about the negated arm. Fifteen negated claims cite two or more sources: paper1 claims t8, t18, t28, t36, t42, t59, t62, t65, t68, t69 and t74, bentonite claims t1 and t4, essay claim t3 and bohemia claim t3. In these claims another cited source may still back part of the changed sentence, so a "supported" verdict on one of them is not always a missed change. They are counted with the other negated claims, exactly as written in sections 5 and 7. After the run, a reader who has seen none of the verdicts writes a source-by-source note (which cited source backs which part of the changed sentence, with quotes) for all fifteen, and all fifteen notes are published with the results. Every missed negation is listed by claim, so a reader can see which ones they are.

## 4. The judges

| Judge | Exact model | Where it runs | Arms it runs |
|---|---|---|---|

The seller that answered is recorded for every request. | All nine arms. |

| Claude Haiku 4.5 | `claude-haiku-4-5-20251001` (named in full, for the same reason) | The same. | r1, r2, r3. |

Only the arms in the last column are registered. Commands for other combinations are not prepared, and adding one later is a new, separately dated addition to this document.

**Why these judges.** Claude Sonnet was chosen as a second judge because it comes from another company than Gemma and costs nothing per request through the Claude subscription. Claude Haiku was added because it uses little enough of the subscription to give a third reading.

**Temperature.** Every Gemma judge call is made at temperature 0, which means the model is asked for its single most likely answer. Temperature 0 does not guarantee the same answer to the same question: a note in the checker's code records that an earlier judge model changed borderline verdicts at temperature 0; in an earlier measurement 16 of 7,936 questions asked more than once got a different decision at least once, although for several of those 16 the different decision came when the same question was asked again on a different date, not by chance (section 11), and the paid calls go to four sellers that run the model on different hardware, where small differences in the arithmetic can change the most likely answer. That is why the Gemma judges also make three unchanged runs (r1, r2 and r3). The Claude command-line program does not accept a temperature setting, so the two Claude judges run at that program's own fixed default, which may let the same question get a different answer more often. Each Claude judge makes three unchanged runs for the same reason: without them, a verdict on which a Claude judge and Gemma differ could be either a real disagreement between the two models or only one judge's own randomness, and one run cannot tell the two apart.

**What the Claude judges get.** For the two Claude judges the runner does three more things: they receive exactly the same judge instructions as Gemma (the checker would otherwise swap in an older instruction written for Haiku); their answers are read with a reader that also accepts an answer wrapped in extra text (the checker's normal reader can take a stray bracket in the prose for the answer); and each call may take up to 600 seconds instead of 240 (240 seconds was measured to cut off answers from Sonnet). For every start, the runner records the path and fingerprint of the Claude program the checker will start, without running it (next paragraph). The Claude program adds its own fixed system text in front of every request; the judge instructions it is given are the same as Gemma's, but the full text the Claude model reads is not identical to what Gemma reads. The model that answered is not recorded separately for each call; we rely on the full model names above, each of which names one model, unlike the short names that move to newer models.

**One version of the Claude program for the whole study.** The Claude program updates itself often: on our computer, version 2.1.287 was installed on 1 October 2026, 2.1.288 on 2 October and 2.1.289 on 4 October. If it changed between two runs, a changed verdict could be the program's doing rather than the judge's, so every Claude run of the study, both judges and all their runs, uses one version. The study keeps a fixed copy of the program file of version 2.1.289 (SHA-256 `a186b99e4a9c88366cd49df2f7dad56c61fc306ef0140b19ee64b7c42a8d1348`, the fingerprint of the file Anthropic's installer placed on our computer), and every Claude start uses that copy. The runner refuses to start when the copy is missing or its fingerprint differs, puts the copy's folder first in the list of places where the checker looks for the program, and refuses to start unless the checker would start exactly that copy. The checker starts the program once for every request, and each start could update it, so the self-update is also switched off for every Claude start (`DISABLE_AUTOUPDATER=1`, recorded for every start). As a further check, the runner refuses to start a Claude judge's r2 or r3 when the program recorded for it is not the one that judge's r1 recorded, or when that judge's r1 recorded none. A written override lets a run past this second check, but not past the first: no program other than the fixed copy can run.

**What a comparison between judges compares.** Here is an example. Suppose paid Gemma judges one claim "supported" and Sonnet judges the same claim "unsupported". It is tempting to conclude that Sonnet, the model, reads this claim differently from Gemma. That conclusion goes too far, because besides the model, three more things differ between a Claude run and a Gemma run:

1. **The Claude program's own fixed text.** We reach Sonnet and Haiku through the Claude program on a Claude subscription, not by sending requests to the model directly. The Claude program puts its own fixed instructions in front of every request, before our judge instructions, and we cannot remove them. Gemma receives only our judge instructions. Both judges get the same judge instructions, but the Claude models also read text that Gemma never sees.
2. **The answer reader.** The answer reader is the small piece of the checker that takes the verdict out of the model's reply. Claude models often put their answer inside a sentence of explanation, so the Claude runs use a reader that also finds an answer surrounded by extra text. The Gemma runs use the checker's normal reader. A reply that one reader accepts might be read differently, or asked again, by the other.
3. **The time limit.** Each Claude call is stopped after 600 seconds and asked again. The checker sets no time limit of its own for a Gemma call; the program library it uses waits up to 6,000 seconds. So a very slow Gemma answer is waited for, while a Claude answer that takes longer than 600 seconds is asked again.

So when a claim's verdict differs between a Claude judge and Gemma, the model or any of these three can be the reason, and our numbers cannot say which one. We therefore report such a change as a disagreement between two whole setups, not as an error of either model, and not as the effect of the model alone. The honest statement is narrower: replacing the whole judging setup changes this share of verdicts.

This does not affect the repeat numbers. Each judge is also compared with itself: Sonnet r1 with Sonnet r2 and r3, and the same for Haiku and for Gemma. Within one judge the model and all three of these stay the same, so a change between its repeats is that judge answering the same question differently.

**Why we keep this difference.** Sending requests to Sonnet and Haiku directly through Anthropic's paid service would remove the extra fixed text and would let every judge use the same answer reader and time limit. We chose the Claude subscription instead, because its runs cost no money per request, and we state the three differences here so that no reader takes a Claude-against-Gemma number for the effect of the model alone.

**Concurrency and services.** Requests run four at a time on OpenRouter and two at a time on the other judges. On OpenRouter, four at a time ran 2,539 requests in an earlier paid run with none refused; on Google's free service, four at a time dropped 4 of 100 claims in an earlier run, so the free judge runs two at a time. The two Claude judges send two requests at a time, the same setting as free Gemma; no other value was measured for them. When requests run side by side, a request of one claim can fail because of the load that other requests put on the service; that claim is then marked as coming from a failed call and is simply asked again (section 6), so this cannot produce a wrong verdict. The two Claude judges themselves run one after the other, never together, Sonnet first and then Haiku, as the author asked on 2 October 2026; both draw on the same subscription allowance, so running them together would not finish the study sooner. A judge on one service and the same model on another service are not interchangeable: an earlier measurement of ours, on 100 rows of a published citation benchmark, found that moving the same Gemma model from Google's free service to the full-precision sellers on OpenRouter changed about 5 verdicts in 100. That is why the free and the paid Gemma runs are reported separately and also compared with each other.

**Installed libraries and the search model.** The runs use the program libraries installed on our computer; section 10 gives the fingerprint of their full list (`pip freeze`), and every start records it again, so a library update during the study would be visible. Before the judge reads anything, the checker picks the candidate source sentences with a search model that runs on our own computer, `sentence-transformers/allenai-specter` at version `2c68eeca61259b2dd70c3f2628219f925df7031a` of its public model repository. Its files and the saved search indexes of the six texts are fingerprinted in our private record and compared before every arm.

**The software.** Every run starts on one computer, with the operating system Ubuntu 24.04.4 and Python 3.12.3; the program libraries installed are recorded for every start (section 1). The judge models run on their services' computers, not on ours; only the search model and the checker's own program run on our computer.

## 5. What we will report, and how each number is computed

**Why these comparisons.** The comparisons below follow one plan. First we measure how often each judge changes its verdict when nothing at all has changed. Then we change one thing at a time and ask whether the verdicts move more than that. Last, we check that the judge still notices a change that should move a verdict. The comparisons fall into four groups:

- **The judge's own randomness (comparisons 1, 2 and 5).** A language model can give a different answer to exactly the same question: paid Gemma might call a claim supported in r1 and unsupported in r2 with nothing changed. Each judge therefore runs three times unchanged. Two runs would give one number, which could be unusually high or low by chance; three runs give three pairs (r2 against r1, r3 against r1, r3 against r2), and so a range, for example "between 2 and 5 claims changed". Each judge gets its own range, because each judge has its own randomness.
- **Changes that should not matter (comparisons 6 and 7).** The arms prompt, shuffle, bias, doubt and reworded each change one thing that should not change any verdict: the wording of the instructions, the order of the evidence, a confident note from the writer, a doubting note from a reviewer, or the wording of the claim. A judge that is not moved by such a change changes no more verdicts than in its own repeats, so each of these counts is read against paid Gemma's range from comparison 1. For example, if the shuffle arm changes 4 verdicts and the repeats ranged from 2 to 5, the order of the evidence did not measurably move the verdicts; if it changed 12, it did. The two notes point in opposite directions so that their results can be told apart. If the confident note moved 6 verdicts and there were no doubting note, a reader could not tell whether the judge leans toward what the writer believes or whether any added sentence at all unsettles it. With both notes, the two can be told apart: if only the confident note moves verdicts, the judge leans toward the writer; if both notes move them, any note unsettles the judge, whichever way it points.
- **A change that should matter (comparison 8).** A judge that called every claim supported would look perfectly stable in all the comparisons above. Stability is worth something only if the judge still notices a real change, so the negated arm turns claims into their opposite and counts how many the judge catches. It is the check on every stability number in this study.
- **A different judge or service (comparisons 3 and 4).** Free Gemma is the judge most users of the free setup get, while the arms run on paid Gemma, so comparison 3 shows whether that difference in service moves verdicts. Comparison 4 shows how much the verdicts depend on which judge is used; as section 4 explains, it compares whole setups, not models alone. Both are also read claim by claim with all three runs of each judge, because a single run mixes claims the two judges really read differently with claims on which one judge simply changes its own answer from run to run.

**Why paid Gemma r1 is the reference.** Every comparison that is not between one judge's own repeats is made against paid Gemma r1, so that all those numbers share one fixed point and can be set side by side. The arms run on paid Gemma, the same model as the free judge, because there the seller and the full-precision copy are fixed and recorded for every request; and because every arm runs on the same judge, exactly one thing differs in each comparison. Next to every comparison of two runs of the same texts we also give accuracy on the changed claims (section 5, "Accuracy"), so a reader can see whether a verdict that moved moved toward the right answer or away from it.

**Changed verdicts.** For every comparison below, we report how many claims were compared, how many changed verdict, and the share as a percentage. The changes are split by direction, each with its own denominator: "green turned red" is given as "X of N claims that were supported in the first run turned unsupported", and "red turned green" as "X of N claims that were unsupported in the first run turned supported". A third column, "other", counts a claim that moved into or out of a class that is neither supported nor unsupported (for example "own", the class of the writer's own uncited words); on these texts we expect it to stay at zero. For the arms that judge the same texts, a claim is paired with itself by its text; two claims of one text with exactly the same words cannot be paired that way, so they are left out and counted in the notes (on earlier runs of these six texts no two claims share their words, so none is left out). For the reworded arm, each reworded claim is paired with its original by position. A claim counts as compared when at least one of the two runs judged it (uncited claims are never compared).

The comparisons:

1. Paid Gemma r2 against r1, r3 against r1, and r3 against r2 (repeats; three pairs).
2. Free Gemma r2 against r1, r3 against r1, and r3 against r2 (repeats on the free service).
3. Free Gemma against paid Gemma (the effect of the service): r1 against r1, and the claim-by-claim reading described below. The dates of the free and the paid runs are stated next to this comparison, because the free runs start days after the paid ones.
4. Sonnet against paid Gemma, and Haiku against paid Gemma (a second judge model): r1 against r1, and the claim-by-claim reading described below. A change here is a disagreement between two whole setups (section 4), not an error by itself.
5. Sonnet r2 against r1, r3 against r1 and r3 against r2, and the same for Haiku (repeats on each Claude judge).
6. Paid Gemma prompt, shuffle, bias and doubt, each against paid Gemma r1.
7. Paid Gemma reworded against paid Gemma r1.
8. Paid Gemma negated: of the negated claims whose original was supported in paid Gemma r1, how many came out unsupported (caught) and how many stayed supported (missed).

**How an arm that ran once is read.** The arms prompt, shuffle, bias, doubt, reworded and negated run once, on paid Gemma. They run once because one paid arm costs about $0.53 to $0.88 (estimated for an arm with the ten hard sentences, from a measured six-text arm that cost $0.52 at the cheapest of the four sellers and $0.87 at the dearest) and takes about 3.3 hours; this was our own decision, made to keep the cost and the time of the study down. Paid Gemma also changes some verdicts with nothing changed at all, so a changed verdict in a one-run arm may be the arm's doing or only the judge's own randomness. Two things separate them. First, every changed verdict of such an arm is sorted claim by claim: "moved by the arm" when paid r1, r2 and r3 all gave the same verdict and the arm differs from all three; "also changed in a repeat" when r2 or r3 already differs from r1 on that claim; "repeats unknown" when a repeat has no usable verdict for it. For example, if the bias arm changes 5 verdicts and on 3 of those claims r1, r2 and r3 agree, we report "5 changed, 3 moved by the arm, 2 also changed in a repeat". Second, the count of changed verdicts of each of the arms prompt, shuffle, bias, doubt and reworded is read against the range of the three repeat pairs of paid Gemma (comparison 1) (the negated arm is read by its catch rate instead, because a changed verdict is what it expects): a count at or below the largest of the three is described as "within the range of the repeats", a larger count as "above the range of the repeats". No test of statistical significance (a standard calculation of how likely a difference this large would be by chance alone) is made for any comparison in this study, and no comparison is described as significant. We make no significance test, because the counts are small (a few changed verdicts among 85 claims), the claims are not independent of each other (claims of the same text share their sources), and each changed arm runs once, so its own spread cannot be measured. A test would give a precise-looking number resting on assumptions this study does not meet. Instead every changed verdict is listed and sorted claim by claim. The consequence is that this study can show a large effect of an arm but cannot rule out a small one: an arm that changes one or two verdicts more than the unchanged repeats cannot be told apart from chance.

**How precise the numbers are.** One claim is about 1.2 percentage points of the 85 judged claims, so no share can be finer than that, and a share of 5% rests on about 4 claims. The shares split by direction rest on fewer claims (for example only on the claims that were supported in the first run), so one claim moves them more; each share is therefore printed with its count. We give no confidence interval (a range that a standard calculation says probably holds the true value) for any share, for the same reasons we make no significance test: the claims are not independent of each other, each changed arm runs once, and the repeats give only three pairs per judge. The range of the three repeat pairs is itself only a rough reference: with three pairs, a fourth repeat could well fall outside it.

**How two judges are compared claim by claim.** For comparisons 3 and 4, a single run of each judge mixes two things: claims on which the two judges really read the evidence differently, and claims on which one of them gives different answers from run to run. Two further counts use all three runs of each judge. The first counts the disagreement only on the claims where all three runs of each judge give the same verdict (and none came from a failed call): a disagreement there is between two judges that each repeat themselves. The second compares majority verdicts: the verdict at least two of a judge's three runs gave, against the other judge's; a claim without a majority on one side is counted apart. A run whose verdict came from a failed call is skipped; a majority then needs the two remaining runs to agree, otherwise the claim is counted as having no majority. For example, if Sonnet and paid Gemma differ on 6 claims in r1 against r1, but on 4 of those 6 one of the two judges changes its own verdict between its runs, the first count shows the 2 claims on which both judges hold steady and still disagree. On every disagreeing claim that has a hand-checked row, both judges' correct counts are given (a judge counts as right on that claim when at least two of its three runs got the row right), next to the number of changed verdicts in each judge's own three repeat pairs on all the claims this comparison pairs. Because of the limit stated in section 2, these correct counts favour Gemma.

**Accuracy.** Next to every run that judged the six original texts, we report how many of the 56 hand-checked rows it got right, using the rules in section 2. For every comparison of two runs of the same texts, we also give, on the changed claims that have a hand-checked row, how many of them each of the two runs got right. The ten hard sentences are reported in their own table, as counts: changed verdicts against r1 of the same judge, and how many of the ten match their expected verdict. As in comparisons 3 and 4, free Gemma r1, Sonnet r1 and Haiku r1 are also compared against paid Gemma r1 on the ten hard sentences, and the claim-by-claim reading is made on them as well.

**The negated arm, three ways.** The catch rate (comparison 8) is given over every counted negated claim, again without the fifteen claims that cite two or more sources (section 3), and again over the claims whose original was supported in all three unchanged paid runs (section 3). Next to it we report the number of claims supported in r1 that have no negated copy, which the negated arm therefore never tests (section 3), with each of them named.

**Every individual change.** Besides the totals, we list every changed verdict and every missed negation with its text, claim number, both verdicts, the claim's words, the sorting above where it applies, and the sellers that answered that claim's requests (section 9).

**Runs that are not clean.** A run in which any call failed is marked "not clean" in the table and is still scored: only the claims whose verdict came from a failed call are left out (section 6). A text whose run record names a different version, an edited copy or a different arm, or that carries no run record of the runner at all (a sign that it was run without going through the runner), is left out of every comparison it is in and named in the notes; the runner's refusals (section 1) should make this impossible, and the scorer checks it anyway.

## 6. Failed calls, used-up allowances and an empty balance

A failed call must never be counted as a verdict, because the checker records a claim whose judge calls all failed as unsupported, which would look exactly like a green card turning red.

- Each run has a built-in second pass that asks again every claim whose call failed. After it, a claim whose verdict still came from a failed call is asked again, pass after pass, until none is left; the author chose on 2 October 2026, before any result existed, to ask a failed claim again until none is left, with the 24-hour limit below for each text. For example, if after the second pass of the bentonite text two claims still have no real answer because the service refused the requests, the runner waits 10 minutes and repeats the pass; the repeat asks only those two claims again and keeps every other claim's verdict as it is; if one of the two still fails, it waits another 10 minutes and repeats again. Each repeat is the checker's own re-run of the same folder. In it, exactly two kinds of claim are judged again, and each one's new answer replaces its old one: a claim marked as coming from a failed call (which can include an unsupported claim that was judged while another of its requests was failing), and a claim whose extra check (for example the partial-support check) failed. Every other claim keeps its verdict and is not asked again. Every pass is logged with the number of claims still failed. The repeats of one text stop when no claim fails; when the run is stopped for an empty balance or a long subscription limit (below), and then nothing more is sent; on paid Gemma, when the arm's spending, priced at the paid test script's rates (the dearest seller's) and summed over all of the arm's folders, is above the arm's spending ceiling, and then no further pass is sent (the test script's own second pass is never held back, as in the unchanged script); after three passes in a row that ended with an error and wrote no result, because a fourth would do the same; or when 24 hours have passed since the second pass began, and then no new pass starts. A claim still failed at that point is named in the results with its text and the error, and is treated as the next item says. A report of claims still failed that an earlier start of the same text left behind is deleted when the repeats begin, so it can never describe a later start.
- The pause and the limit are our own choice, not measured values. A repeat pass starts only after the checker's own retries inside each request have failed; the outages we have seen on these services lasted from about a minute to about a quarter of an hour, so a 10-minute pause lets a short outage pass. A service that still fails after a day has a lasting problem, so the repeats stop after 24 hours, and the claims still failed are named and left out rather than holding up the rest of the study.
- Every paid arm has a spending ceiling of $1.60. Once an arm's spending is above it, the runner sends no further repeat pass, counting every folder of the arm, and the paid test script starts no further text. The test script counts only the texts of its own start, so when an arm is started again after a stop for its unfinished texts, the arm's total can go above the ceiling by at most what those unfinished texts cost. We set it above the measured cost of a six-text arm ($0.52 at the cheapest seller to $0.87 at the dearest), above the estimated cost of an arm that also judges the ten hard sentences ($0.53 to $0.88), and above the estimated, not measured, cost of the negated arm (up to $1.16), so that it should not cut an arm short; it is a stop against a fault, and money is spent only as far as an arm needs it.
- A free Gemma run also stops when it reaches a limit of 48 hours, which this study sets for each of its entries in our queue of free jobs (the queue's own default is 12 hours): a free run takes about 11 hours, and the repeats of one text may add up to 24 hours more. The same command is then queued again: the texts already finished are kept, and the text that was interrupted is judged again from its first claim.
- A claim whose verdict still came from a failed call, in either of the two runs being compared, is left out of that comparison and out of the accuracy, and the number left out is published in its own column. Such a claim is never counted as a changed verdict or a wrong row. A claim is marked as coming from a failed call only when its verdict is "unsupported" (the checker stores a claim whose judge requests all failed as unsupported, while a "supported" verdict always rests on a real positive answer, even if some other request on that claim failed), so the claims left out are always unsupported ones. If many are left out, the published counts can therefore under-count changes towards unsupported; the number left out is published so a reader can see how large that effect could be.
- When the Claude subscription's allowance is used up in the middle of a run, the call waits and then asks again, so no failed call is recorded. When the service's message names the reset as a time of day, the call waits until that time plus two minutes; when it names a weekday or a date instead, which a weekly limit usually does, the message is not read for a time, and the call waits 10 minutes and asks again, as often as needed. Every wait is logged. If the waiting would last more than 6 hours in all, the run stops instead; the text that was being judged is then judged again from its first claim after the reset, and nothing half-judged is kept.
- When the OpenRouter balance runs out, the run stops at once, before anything from the refused request can be stored, and nothing more is sent until the balance is topped up. Before each text starts, the runner also reads the balance and does not start the text while it is below $0.30. The text that was being judged is then judged again from its first claim.
- How "judged again from its first claim" is made true: a stopped text never writes its result file, and the checker's save-as-you-go record of the stopped start (which the checker would otherwise reuse) is moved aside by the runner, unread, before the next start. The texts already finished are not judged again.
- A run is stopped only for these reasons, for a crash, or at a stop time set before the run starts; it is never stopped or repeated because of the verdicts it produces. One run was stopped at a set time: Sonnet r1, at 01:00 on 3 October 2026, at the author's request made before it started (section 9). That partial run is not used; Sonnet r1 starts again from zero (section 9).

## 7. What counts as expected and what as an error

In comparisons 1 to 3 and 5 to 7, nothing that matters to the verdict has changed, so every changed verdict counts as instability, in either direction. In comparison 3 only the service changes (the same model, the same instructions and the same texts, answered by Google's free service instead of the paid sellers), so a changed verdict there counts as instability too, and it is also read with the claim-by-claim reading of section 5, as in comparison 4. In the bias arm, a red card turning green is the direction of most concern, because it means a confident tone moved the judge; both directions are reported. In the doubt arm, a green card turning red (supported turning unsupported) is the direction of most concern, because it means a doubting tone moved the judge; both directions are reported here too. In comparison 4, changes are disagreements between two setups and are read together with the claim-by-claim reading of section 5 (stable claims, majority verdicts and the correct counts on the disagreeing claims). In the negated arm, a change from supported to unsupported is the expected result and counts as a catch; a negated claim that stays supported counts as a miss. A negated claim whose original was already unsupported in r1 tells nothing and is not counted.

We set no pass mark in advance. Any number we picked now would be a guess, and the purpose is to report what happens. The numbers are published as they come out.

**The headline numbers.** Two numbers lead the results: the number of verdicts paid Gemma changed between its own unchanged runs (comparison 1, its three pairs), and the negated arm's catch rate (comparison 8). Every stability number is shown next to the catch rate, because a judge that does not read the claims carefully could look perfectly stable (section 5, "A change that should matter"). If the catch rate is low, we state next to the stability numbers that they cannot show that the judge reads the claims. For the reason just given, we fix no number for "low" in advance; the catch rate and every missed negation are published, so a reader can judge it.

## 8. Our promise, and where the results appear

We will publish the numbers of every arm listed here, whatever they show, including arms that show the checker in a bad light, and including any arm that could not be finished, with the reason it could not. We will not add, drop or redefine an arm or a count after seeing a result; if we find a mistake in the method, we will publish the correction next to the original numbers, never instead of them. With the numbers we will publish the counting program, the lists of arms it reads, the changed texts, the answer keys, and the counting program's full output: every total per arm, the counts of claims left out and why, the accuracy, and a list of every changed verdict and every missed negation, each with its claim number, the claim's whole words and both verdicts. A reader can check the totals against those lists and against the texts. To recount the compared counts or the accuracy, a reader needs the checker's full result files, because those are what the counting program reads; the full result files quote passages from the sources. So they are published text by text, by one rule: a text's full result files are published when every one of its sources is under an open licence that allows the quoted passages to be republished, and never when any of its sources is under a licence that does not allow it or is behind a paywall. For example, the bentonite text cites two subscription articles (section 2), so its full result files are never published. Before the results are published we check the licence of every source of every text; the list of the texts whose full result files are published, with the licence of each of their sources, is published with the results. For the other texts the full result files are shown on request, and for them a reader cannot recount the compared counts or the accuracy alone. The ten constructed hard sentences fall under the published side: their two sources are test documents constructed for this study (they say so in their first lines), so their full result files are published. Three working files of the study are not part of the published study folder, because they hold paths of our own computers: the list of start commands (which also holds blank places for the author's approval), the private fingerprint record (which also names the program files and sources that stay private; every fingerprint that can be published is printed in section 10), and the saved result of the no-request check that every switch is read (which also names the location of the study's copy of the Claude program). Every arm's settings are published in the lists of arms the counting program reads, and the program that makes the no-request check is published, so anyone can repeat that check.

The results, the runner, the scorer and the changed texts are published as a folder of our public repository, on or after the day of the release named in section 1, and announced in a dated post. Every number names the release tag.

**Analyses not in this plan.** Any count or comparison that section 5 does not describe is published under a heading that marks it as exploratory, apart from the planned results, and it is never used to change how a planned number is read.

**Changes after publication.** If anything is done differently from this plan after it is published, the results carry a dated table of every such change: what this plan said, what was done instead, why, when (before or after any result of the study had been seen), and what effect it has on the numbers. At publication the table is empty. What happened before publication is described in this plan itself (section 9).

**How the date of this plan can be checked.** This plan is published only in our public repository, in a commit tagged `stability-2026-10`; the tag's name carries only the month, and the commit's own date is the date of publication. It is not deposited in an outside archive. A repository's history can be changed by its owner, so the tag alone does not prove to an outsider that this text was not edited after that date.

## 9. Schedule, and what happens if a model changes

**Order.** Every run that counts starts after this document is published; the one partial run described below is not used. The paid Gemma arms start only after the author gives a new go for them, once everything is ready. ## 10. Fingerprints

The files below are the ones the arms use that can change a verdict or a reported number and that will be public, so a reader can recompute every fingerprint listed here, with one exception: the five program files the release changes (section 1, "The release") are listed apart, each with the fingerprint of its measured version, which a reader cannot recompute from the public files and which we show on request against the file itself, and the fingerprint of its released version, which a reader can recompute. The combined fingerprint of the measured checker covers only the program files the release holds unchanged. The files of the measured checker were fingerprinted on 2 October 2026, before any arm was started; the study's own files that changed afterwards were fingerprinted again on 5 and 6 October 2026, and section 9 ("What had already run when this plan was published") gives the earlier fingerprint of every study file that changed. The fingerprints were computed by the program `fingerprints.py`, which is published with the results and recomputes all of them; a reader who lacks some of our files gets a note for each missing file and the rest is still computed.

A file's fingerprint is the SHA-256 of its exact bytes, which is what the standard `sha256sum` command prints. A "combined" fingerprint is the SHA-256 of a text in UTF-8 with one line per file, each line being the file's relative path, two spaces and the file's SHA-256, each line ending in a newline, the lines sorted by path in byte order (the order `LC_ALL=C sort` gives). Paths are relative to the root of the measured copy for program files. For the hard sentences they are relative to the folder `hard_rows/`, and the file of their expected verdicts, which sits next to that folder, is added under the path `hard_rows_ground_truth.json`. (This is not the same as feeding `sha256sum`'s own output into `sha256sum`, because `sha256sum` writes the fingerprint before the path.) Caches and compiled `.pyc` files are skipped.

Three kinds of file get no published fingerprint, because a reader could not recompute it. The program files that will not be public (section 1 explains why none of them can change a verdict or a reported number). Other people's source documents (section 2). And the inputs that exist only on our computer: the saved search indexes and the files of the search model (section 4). For all three we keep the fingerprints in a private record; the check run right before each arm and the runner at the start of each text compare the inputs with it (section 2), and we show any of these fingerprints on request.

The last column says what happens to each file: "already public" (in the public repository now, byte for byte) or "published with the results".

## 11. How this connects to the rest of our evaluation

Earlier, smaller measurements already exist and are not replaced by this one. In one of them we asked the free Gemma judge 7,936 different questions more than once each; for 16 of those questions the judge gave a different decision at least once, and for several of those 16 the different decision came when the same question was asked again on a different date, not by chance. In another, on 100 rows of a published citation benchmark, moving the same Gemma model from Google's free service to the full-precision sellers on OpenRouter changed about 5 verdicts in 100. This study adds the arms no earlier measurement had (a reworded instruction, a shuffled order, a confident-writer note, a doubting-reviewer note, reworded and negated claims, a second judge model) and puts every one of them next to the accuracy on the same texts, for the same version of the checker.
